# Аналитика UTMka

Контур из трёх частей: **события в коде → цели в Метрике → отчёт на диске**.
Ничего не деплоится, ничего не крутится на сервере: сбор запускается руками с
машины владельца, отчёт — обычный HTML-файл рядом с кодом.

Заведено 2026-08-28.

---

## Быстрый запуск

```bash
python -X utf8 scripts/analytics_pull.py      # снять данные (по умолчанию 90 дней)
python -X utf8 scripts/analytics_report.py    # собрать docs/analytics/report.html
```

Отчёт открывается двойным кликом: [docs/analytics/report.html](analytics/report.html).
Снимки складываются в `docs/analytics/data/` — под датой (история) и как
`latest.json` (из него рисуется отчёт).

Сверить цели в панели со списком событий в коде:

```bash
python -X utf8 scripts/analytics_goals.py             # показать разницу
python -X utf8 scripts/analytics_goals.py --apply     # применить
```

## Что считается целью

Событие — это **полученный результат**, а не нажатая кнопка. Открытый экран
целью не является, скопированная ссылка — является.

Список живёт в [`packages/core/src/track.ts`](../packages/core/src/track.ts) и
оттуда же читается скриптом целей. Переименование события — всегда парой:
в коде и в панели, иначе цель молча перестанет достигаться.

| Событие | Когда стреляет | Где в коде |
|---|---|---|
| `link_copied` | ссылка ушла в буфер (после успеха, не по нажатию) | `ResultCard.tsx` |
| `batch_done` | пакет скопирован или выгружен в CSV, с корзиной размера | `BatchScreen.tsx` |
| `parse_done` | первый разбор за заход на экран | `ParseScreen.tsx` |
| `short_made` | clck.ru вернул короткую ссылку | `LinkTools.tsx` |
| `qr_saved` | QR выгружен в SVG или PNG | `LinkTools.tsx` |
| `template_saved` | шаблон сохранён | `SaveBar.tsx` |
| `assistant_used` | помощник ответил (отказ по квоте не считается) | `Assistant.tsx` |
| `passphrase_created` | заведена кодовая фраза | `LoginScreen.tsx` |
| `desktop_click` | уход в версию для компьютера | `DeviceFrame.tsx`, `HelpScreen.tsx` |

### Как событие доезжает до счётчика

Через границу оболочки, как всё остальное внешнее:

```
экран → track() из '../shell' → алиас #shell
                                  ├── apps/web:     window.ym(id, 'reachGoal', …)
                                  └── apps/desktop: пустая функция
```

Аналитики в окне Tauri нет и не будет: приложение обещает работать офлайн и не
ходить в сеть само. Пустая реализация нужна, чтобы экраны звали `track` без
проверок «а мы в вебе?» — такой проверки внутри экрана как раз и не должно быть.

### Чего в событиях нет

Ни адресов, ни значений меток, ни кодовой фразы. Параметр у события ровно один
— корзина размера пакета (`1-10`, `11-50`, `51-200`, `200+`). Это то же правило,
по которому в счётчике выключен вебвизор: в полях инструмента живут реальные
кампании пользователей.

Площадку в параметры не кладём намеренно: у каждой посадочной свой адрес
(`/tilda`, `/vk`), и разрез «цель по странице входа» в отчёте отвечает на тот же
вопрос — какая посадочная приводит людей, доходящих до результата.

**Событий без согласия не бывает.** Пока человек не ответил на плашку, компонент
`Metrika` не рендерит сниппет, `window.ym` не существует, и `track` тихо ничего
не делает.

## Откуда берутся данные

| Источник | Что даёт | Доступ |
|---|---|---|
| Яндекс.Метрика | визиты, источники, страницы входа, достижения целей | `YANDEX_OAUTH_TOKEN` |
| Яндекс.Вебмастер | страницы в поиске, запросы с позициями, диагностика | `WEBMASTER_OAUTH_TOKEN` |
| Google Search Console | показы, клики, позиции, состояние sitemap | gcloud ADC на машине |
| Supabase | ссылки, аккаунты, шаблоны, справочник — факт, а не визит | `apps/web/.env.local` |

Токены Яндекса ищутся сначала в переменных окружения, потом в
`welcome/analytycs-welcome/.env` (там они лежат исторически). Переехали —
задайте `UTMKA_YANDEX_ENV`. Копию токена в этот репозиторий не кладём: два
экземпляра секрета протухают по очереди.

Для Google нужен живой ADC. Протух — `gcloud auth application-default login`.
Путь к gcloud переопределяется переменной `UTMKA_GCLOUD`.

Ни один источник не обязан ответить. Молчащий записывает в снимок причину, а
остальные собираются как ни в чём не бывало — иначе спящая база уносила бы с
собой данные Метрики.

### Зачем база рядом со счётчиком

Счётчик видит визиты и только тех, кто согласился на куки. База видит результат:
сколько ссылок собрано, чем именно (генератор, пакет, помощник, разбор), сколько
аккаунтов и шаблонов. Расхождение между ними само по себе полезно — оно
показывает, какую долю работы счётчик не видит.

## Что в отчёте

* **Сигналы** — то, на что смотреть глазами: провал индексации, цели без
  достижений, проблемы из диагностики Вебмастера, недоступная база. Правила
  грубые и молчат, когда всё в порядке.
* **Итоги периода** — плитки и визиты по дням.
* **Поиск** — страницы в поиске Яндекса, запросы обеих панелей, поисковые фразы.
* **Трафик** — страницы входа с достижениями главной цели, источники, устройства.
* **Целевые действия** — достижения по каждой цели.
* **Продукт** — числа из базы.

Отчёт самодостаточен: ни одного внешнего запроса, светлая и тёмная темы,
открывается с диска. Графиков ровно два, и оба одиночные — при нынешних числах
любая вторая линия была бы украшением.

## Настройки, которых нет в API

Две рекомендации Вебмастера ставятся **только руками в панели** — API v4 их не
отдаёт вовсе (`RESOURCE_NOT_FOUND`):

* Индексирование → **Обход по счётчикам Метрики** (счётчик 111529339);
* Информация о сайте → **Региональность**.

Обе висят в сигналах отчёта, пока не выставлены.

## Что ещё нельзя автоматизировать

Запросить переиндексацию URL в Google по API нельзя (Indexing API — только для
вакансий). Свежий sitemap остаётся главным сигналом, точечная переиндексация —
руками в «Проверке URL». В Яндексе переобход есть: квота ~150 адресов в сутки.

## Сторож базы (чтобы не уснула снова)

28.08.2026 Supabase-проект оказался **на паузе**: Free-тариф усыпляет базу, если
за неделю к ней «недостаточно пользовательских запросов». У UTMka это случается
легко — генератор, пакет, разбор и QR целиком работают в браузере, в базу ходят
только вход, шаблоны, история и справочник. Трафик на сайте был, запросов к базе
не было. Итог: у людей молча не работали вход и сохранение, а `/api/session`
при этом отвечал `storage: true` — он проверяет наличие переменных окружения,
а не живость базы.

Лечится сторожем на боксе: [`scripts/keepalive.sh`](../scripts/keepalive.sh) →
`/usr/local/sbin/utmka-keepalive.sh`, крон **три раза в сутки** (06:10, 12:10,
18:10 UTC), лог `/var/log/utmka-keepalive.log`.

```bash
/usr/local/sbin/utmka-keepalive.sh              # пинг
/usr/local/sbin/utmka-keepalive.sh --test-alert # проверить, что канал алерта жив
```

**Почему читает, а не пишет тестовую запись.** Активностью считается любой
запрос к базе, а не изменение данных — так написано в документации Supabase
(«a few user requests to the database each day»). Запись пришлось бы заводить в
боевые таблицы с данными живых людей и потом убирать за собой: сбой посреди
уборки оставил бы мусор в проде, а `links` ещё и ссылается на `users` внешним
ключом — одной фиктивной строкой не обошлось бы. Чтение даёт тот же эффект.

**Почему три раза в день, а не раз в двое суток.** Документация говорит про
несколько запросов **каждый день**; редкий пинг формально активность создаёт,
но под порог «низкой активности» проект всё равно может попасть.

**Разбудить уснувшую базу сторож не может** — паузу снимает только
восстановление проекта (дашборд Supabase → Resume project, либо Management API).
Поэтому вторая его работа — сказать, что база легла: сообщение уходит в Telegram
владельцу через бота трекера (`/opt/tracker/.env`, прямой `api.telegram.org` с
бокса режет ТСПУ, поэтому через прокси оттуда же). Нет файла бота — сторож не
падает, а пишет в лог: он не должен ломаться из-за отсутствия способа пожаловаться.

Второй, независимый сигнал — блок «Продукт» в отчёте: сборщик ходит в базу и
пишет причину отказа.

Радикальная альтернатива — Pro-план ($25/мес): платные проекты не паузятся
вообще. Пока данных на три аккаунта, сторож дешевле.
