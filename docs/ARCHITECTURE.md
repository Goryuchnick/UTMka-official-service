### 1.1 Источник правды по механике — десктоп 2.2, не сайт

Решение владельца 2026-08-10. **Работающее приложение 2.2.1** (Flask + PyWebView, GitHub Releases)
— полноценный, обкатанный продукт: генератор, история, шаблоны с тегами и цветами, три режима
отображения, поиск, импорт/экспорт JSON и CSV, сокращатель, QR с выгрузкой в SVG/PNG, помощь,
две темы, RU/EN, OTA-обновления. Всё это и есть спецификация поведения для 3.0.

Веб-конструктор на сайте (`components/tools/UtmkaApp.tsx`, 600 строк) — **эксперимент с дизайном,
а не продукт**: там нет шаблонов, тегов, импорта-экспорта, режимов отображения и половины логики.
Его механику **не берём вообще** — ни как основу, ни как ориентир.

⚠️ **Что происходит с сайтом (ШАГ 5):** инструмент со страницы `/tools/utmka` **удаляется**.
Остаётся лендинг (описание, ошибки UTM, примеры для Директа и ВК, FAQ, кнопка на субдомен),
блок офлайн-версии `UtmkaOffline.tsx` и — по мере появления — кейс и статья в блоге.
Кейса про UTMka в `cases-manifest.ts` сейчас нет, статья живёт в Sanity — их состояние сверим на ШАГЕ 5.

## 2. Раскладка репозитория

npm workspaces — тот же инструмент, что во всех остальных проектах, без pnpm/turbo.

```
products/UTMka-official-service/
├─ package.json                 # workspaces: ["packages/*", "apps/*"]
├─ packages/
│  └─ core/                     # @utmka/core — чистый TS, ноль рантайм-зависимостей
│     ├─ src/
│     │  ├─ types.ts            # UtmParams, Issue, Preset, DictEntry, Template…
│     │  ├─ build.ts            # сборка ссылки
│     │  ├─ parse.ts            # разбор чужой ссылки
│     │  ├─ validate.ts         # правила §2.1 ASSISTANT-SPEC, каждая с последствием
│     │  ├─ normalize.ts        # «привести в порядок» + транслит, всегда до/после
│     │  ├─ dictionary.ts       # справочник, автодополнение, детектор расщепления
│     │  ├─ presets/            # Директ, ВК, Telegram Ads, email, офлайн/QR
│     │  ├─ batch.ts            # таблица площадок → пакет ссылок, CSV in/out
│     │  ├─ redirect.ts         # чистая логика цепочки (fetch инжектится снаружи)
│     │  ├─ repository.ts       # интерфейс хранилища (см. §5)
│     │  └─ index.ts
│     └─ test/                  # vitest, покрытие ядра — обязательное
├─ apps/
│  ├─ web/                      # Next.js 16 App Router, TS strict
│  └─ desktop/                  # Tauri — заводим на ШАГЕ 7+, сейчас не создаём
├─ legacy/
│  └─ desktop-2.2/              # весь нынешний Python + frontend + installers, заморожен
└─ docs/
```

**Перенос легаси делаем одним коммитом `chore: заморозить 2.2 в legacy/`** до начала работы над core:
в корень уезжают только `package.json`, `packages/`, `apps/`. Внутри `legacy/desktop-2.2/` пути
относительные, сборка 2.2 продолжает работать оттуда без правок.

**Почему монорепо, а не отдельный репозиторий под веб:** слой правил обязан быть один на все
оболочки — иначе десктоп и веб разъедутся в проверках, а это ровно то, что мы продаём.
Отдельный репозиторий потребовал бы публикации `@utmka/core` в npm-реестр ради одного потребителя.

⚠️ **Репозиторий публичный** (`github.com/Goryuchnick/UTMka-official-service`) — ни ключей,
ни `.env`, ни дампов. Секреты живут только в `/opt/stack/env/utmka.env` на боксе.

## 3. Слои и направление зависимостей

```
              ┌───────────────────────────────────────┐
              │  @utmka/core — правила, ноль сети,    │
              │  ноль DOM, ноль зависимостей          │
              └───────────────┬───────────────────────┘
                  ┌───────────┴────────────┐
        apps/web (Next.js)          apps/desktop (Tauri, позже)
        ├ UI (1:1 из макета)        ├ тот же UI
        ├ репозиторий: Supabase     ├ репозиторий: SQLite
        ├ слой 1: сеть (роуты)      ├ слой 1: сеть (Rust-команды)
        └ слой 2: LLM (routerai)    └ слоя 2 нет
```

Правило: **core ничего не знает о Next.js, Supabase, `fetch`, `window` и `localStorage`.**
Всё, что требует внешнего мира, принимается параметром (fetcher, репозиторий, часы).
Это условие того, что core тестируется и переезжает в Tauri без переписывания.

**Ассистент — не отдельный слой, а потребитель core.** Реплики маскота на правилах строятся
из тех же `Issue`, что подсвечивает форма: у каждой проверки есть машинный код, короткий текст
для инлайна и развёрнутый — для маскота.

**Ответ LLM всегда проходит через `validate` + `normalize` перед показом** — правило из
ASSISTANT-SPEC §3, реализуется единственной точкой входа `assistant/brief` на сервере,
обойти её из UI невозможно.

## 4. Web: маршруты и API

### 4.1 Паритет с 2.2 — что обязано доехать 1:1

Ничего из этого списка не «упрощается по дороге»: это работающие функции, за которые
пользователей уже приучили.

| Функция 2.2 | Деталь, которую легко потерять |
|---|---|
| Генератор | 5 полей + базовый URL, счётчик длины, копирование как главное действие |
| Date-picker в полях campaign/content/term | flatpickr с кнопкой «Сегодня»; дата **дописывается** к значению через `_`, не заменяет его |
| История | поиск + **три режима отображения** (список / плитки / таблица), режим запоминается |
| Шаблоны | имя, тег с **цветом из палитры**, подсказки «популярные» и «недавние» теги, поиск, те же три режима |
| Быстрый старт | недавние шаблоны прямо на экране генератора |
| Импорт/экспорт | JSON и CSV, обе стороны; образцы `templates_example*.json/csv` в репо |
| Сокращатель | внешний сервис, результат подставляется в карточку ссылки |
| QR-код | генерация + сохранение **в SVG и в PNG** |
| Модалка ссылки | детали + действия «сократить», «QR», «применить в генератор» |
| Помощь | встроенный раздел, не ссылка наружу |
| Темы и язык | светлая/тёмная, RU/EN, выбор сохраняется |
| Потолки | 500 записей истории и шаблонов на пользователя |

Новое в 3.0 поверх этого — валидация в момент ввода, нормализация, справочник значений,
разбор чужой ссылки, пакетный режим, пресеты площадок, проверка редиректов, ассистент.

### 4.2 Три способа собрать ссылку — не путать между собой

Это разные задачи, а не разные уровни одной. Различаются **объёмом работы**, а не сложностью
интерфейса:

| | Что делает | Кому |
|---|---|---|
| **Простой режим** | одна ссылка, пошагово, вопросами на человеческом языке | новичок, телефон, «надо разово» |
| **Расширенный режим** | одна ссылка, все поля сразу — как в 2.2 | тот, кто знает, что такое `utm_term` |
| **Пакетный режим** | 20 ссылок за заход, таблицей, с выгрузкой в CSV | запуск кампании на много площадок |

Простой и расширенный — **два вида одного экрана генератора**, переключаются тумблером
и делят одну модель данных: переключение не теряет введённое. Пакетный — отдельный экран.

#### Простой режим — как устроен

Не урезанная версия расширенного, а **другая формулировка тех же полей**: вместо имён
параметров — вопросы, вместо ввода руками — готовые кнопки.

1. **«Куда ведёт ссылка?»** — одно поле URL, больше на шаге ничего нет.
2. **«Откуда пойдут люди?»** — крупные плитки площадок: Яндекс.Директ, ВКонтакте,
   Telegram-канал, Telegram Ads, email-рассылка, QR/офлайн. Нажатие подставляет пресет
   из core — `source`, `medium` и динамические подстановки разом. Плитка объясняет
   одной строкой, почему `vk` это площадка, а `social` — тип трафика (ASSISTANT-SPEC §2.6).
3. **«Как назовём кампанию?»** — одно поле, подсказки из справочника и быстрые чипсы
   (месяц, прошлые названия). Шаг «уточнить `content` и `term`» — свёрнут, по желанию.
4. **Готово** — ссылка, копирование, QR, предложение сохранить.

Валидация, нормализация и справочник — **те же самые**, из core. Простой режим не «прощает»
ошибок, он просто задаёт вопросы иначе. Маскот на шагах комментирует последствия
(«в Директе без `{keyword}` ты не увидишь, по каким запросам шли показы»).

Дефолт для первого визита — простой; выбор запоминается в настройках. Для телефона
простой режим — основная раскладка. Ссылка `?mode=simple|pro` перебивает сохранённый выбор,
чтобы можно было кинуть коллеге «открой сразу в простом».

### 4.3 Маршруты

| Маршрут | Экран | Вход нужен |
|---|---|---|
| `/` | Генератор: простой / расширенный (копирование — главное действие) | нет |
| `/batch` | Пакетный режим | нет |
| `/parse` | Разбор чужой ссылки | нет |
| `/library` | Шаблоны, справочник значений, история | **да** |
| `/login` | Кодовая фраза: вход и генерация новой | — |
| `/help` | Что такое UTM, пресеты, объяснения параметров | нет |

Админка (`/admin` за `ADMIN_LOGIN_TOKEN`, счётчики использования без ПД) —
**вне объёма v3.0**, закладываем только место в маршрутах.

| API | Назначение | Доступ |
|---|---|---|
| `GET /api/health` | health-check для Docker | — |
| `POST /api/session` · `DELETE /api/session` | вход по фразе / выход | — |
| `GET/POST/PATCH/DELETE /api/templates` | шаблоны | только с сессией |
| `GET/POST /api/dictionary` | справочник значений | только с сессией |
| `GET/POST /api/history` | история ссылок | только с сессией |
| `POST /api/shorten` | сокращение (перенос из pronin) | без сессии, rate-limit по IP |
| `POST /api/redirect-check` | проверка цепочки редиректов | без сессии, rate-limit по IP |
| `POST /api/assistant/brief` | бриф → пакет меток (LLM) | **только с сессией**, квота |

⚠️ **`/api/redirect-check` — SSRF-вектор** (сервер ходит по URL, который дал пользователь).
Обязательны: только схемы `http/https`, отказ по приватным диапазонам (10/8, 172.16/12,
192.168/16, 127/8, 169.254/16, `::1`, `fc00::/7`) с проверкой **на каждом хопе**, максимум 10 хопов,
таймаут 5 с, ответ не читаем дальше заголовков. Это первый пункт для `/secure-audit` на ШАГЕ 6.

## 5. Модель данных

Единый интерфейс в core, две реализации — так десктоп получит SQLite без правки UI:

```ts
interface UtmkaRepository {
  templates:  CrudPort<Template>
  dictionary: DictPort            // upsert значения, счётчики, алиасы
  history:    HistoryPort         // добавить, список, лимит 500
  settings:   SettingsPort
}
```

### 5.1 Без входа (по умолчанию)

**Ничего пользовательского не сохраняется** — решение владельца 2026-08-10: шаблоны, справочник
и история открываются только после входа по кодовой фразе. В `localStorage` живут исключительно
настройки интерфейса: `utmka.settings.v1` (тема, язык, режим отображения таблиц).

Это упрощает архитектуру заметно: нет второго хранилища с теми же сущностями, нет слияния
локального с облачным при первом входе, нет расхождения «на этом устройстве одно, в облаке другое».
Инструмент без входа полностью рабочий — просто результат живёт до закрытия вкладки.
Чтение настроек — через `useSyncExternalStore` с кэшем по raw-строке (иначе бесконечный
ре-рендер — грабли из курса).

В **десктопе** этой развилки нет вовсе: там пользователь один и локальный, всё пишется
в SQLite без всякого входа. Именно поэтому хранилище спрятано за интерфейсом (см. ниже).

### 5.2 После входа — Supabase

**Проект — существующий `vmrqocznhydwmkkaochf`** (тот же, где живёт курс; решение владельца
2026-08-10). Чтобы таблицы двух сервисов не перемешивались в `public`, UTMka занимает
**отдельную схему `utmka`**:

- схема добавляется в PostgREST → *Exposed schemas* (одна настройка в дашборде);
- клиент создаётся как `createClient(url, serviceRoleKey, { db: { schema: 'utmka' } })` —
  дальше код не отличается от pronin, имена таблиц без префиксов;
- миграции этого сервиса лежат **в этом репозитории**, `apps/web/supabase/migrations/`,
  и нумеруются `utmka_0001_init.sql`, `utmka_0002_…` — общая база, но чужая нумерация курса
  (`0001…0010`) не пересекается и в глазах не двоится.

Все запросы идут **только с сервера под service-role**; RLS включён, политик для `anon`
нет вовсе. Публичный anon-ключ приложению не нужен.

⚠️ **Остаточный риск общего проекта:** `SUPABASE_SERVICE_ROLE_KEY` один на оба сервиса, то есть
дыра в UTMka технически достаёт и до данных курса (`anon_users`, `lesson_progress`, `bookmarks`).
Схема этого не чинит — service-role видит всю базу. Смягчение, если захотим позже: отдельная
роль `utmka_service` с грантами только на схему `utmka` и свой JWT под неё вместо общего ключа.
Пока держим это как пункт на `/secure-audit` (ШАГ 6), а не как работу v3.0.

```sql
-- владелец кодовой фразы. Никаких ПД: только HMAC фразы.
users (
  hash         text primary key,          -- HMAC-SHA256(passphrase, UTMKA_PASSPHRASE_HMAC_SECRET)
  created_at   timestamptz not null default now(),
  last_seen_at timestamptz not null default now(),
  settings     jsonb not null default '{}',
  is_blocked   boolean not null default false
)

templates (
  id         uuid primary key default gen_random_uuid(),
  user_hash  text not null references users(hash) on delete cascade,
  name       text not null,
  base_url   text not null default '',
  params     jsonb not null,              -- {source, medium, campaign, content, term}
  tag_name   text,                        -- тег и его цвет — паритет с 2.2,
  tag_color  text,                        -- палитра из восьми цветов
  preset_id  text,                        -- id пресета площадки из core, не FK
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (user_hash, lower(name))
)

dict_values (                             -- справочник: ядро продукта
  id           uuid primary key default gen_random_uuid(),
  user_hash    text not null references users(hash) on delete cascade,
  kind         text not null check (kind in ('source','medium','campaign','content','term')),
  value        text not null,
  uses         int  not null default 1,
  canonical    text,                      -- заполнено → это алиас канонического значения
  first_seen_at timestamptz not null default now(),
  last_used_at  timestamptz not null default now(),
  unique (user_hash, kind, value)
)

links (                                   -- история, потолок 500 на пользователя
  id         uuid primary key default gen_random_uuid(),
  user_hash  text not null references users(hash) on delete cascade,
  url        text not null,
  base_url   text not null,
  params     jsonb not null,
  short_url  text,                        -- появляется после сокращения (как в 2.2)
  tag_name   text,
  tag_color  text,
  origin     text not null check (origin in ('single','batch','brief','parse')),
  batch_id   uuid,                        -- группирует пакетный прогон
  created_at timestamptz not null default now()
)

llm_usage (                               -- видимая квота ассистента
  user_hash text not null references users(hash) on delete cascade,
  day       date not null,
  used      int  not null default 0,
  primary key (user_hash, day)
)

rate_limits (key text primary key, count int not null, window_started_at timestamptz not null)
```

Индексы: `templates(user_hash)`, `dict_values(user_hash, kind)`, `links(user_hash, created_at desc)`.
Потолок истории — чисткой при вставке (как в 2.2), не триггером.

**Пресеты площадок в БД не хранятся** — это код в `core/presets`, он должен быть одинаков
в вебе и десктопе и версионироваться вместе с правилами.

### 5.3 Граница «без входа / со входом»

| | Без входа | С кодовой фразой |
|---|---|---|
| Генератор, валидация, нормализация | ✅ | ✅ |
| Пресеты, пакетный режим, разбор ссылки, QR, сокращатель | ✅ | ✅ |
| Проверка редиректов | ✅ (лимит по IP) | ✅ |
| **Ассистент на правилах** (реплики маскота) | ✅ | ✅ |
| **Шаблоны** | ✖ | ✅ |
| **Справочник значений** | ✖ | ✅ |
| **История** | ✖ | ✅ |
| **Импорт/экспорт JSON и CSV** | ✖ | ✅ |
| **Ассистент LLM** (бриф → пакет) | ✖ | ✅ N в сутки |

Всё, что **хранится**, — за фразой. Всё, что **считается здесь и сейчас**, — открыто.
Граница проходит ровно по этой линии, без исключений, поэтому её легко объяснить в интерфейсе
одной строкой: «Чтобы сохранить — заведи кодовую фразу. Это одно поле и никакой почты».

LLM тоже за фразой: это единственный платный ресурс, квоту на анонима не посчитать.
Кончилась квота — инструмент работает дальше без подсказок, без драмы.

⚠️ **Обратная сторона решения, о которой надо помнить в дизайне:** пользователь без фразы,
собравший ссылку, теряет её при закрытии вкладки. Экран генератора обязан предлагать
сохранение **до** того, как человек уйдёт, — это и главный мотив завести фразу,
и главный риск обидеть новичка. Проектируем это как приглашение, а не как стену.

## 6. Слой LLM

routerai (RU-доступный шлюз, OpenRouter отдаёт 403 с российских дата-центров),
модель по умолчанию `qwen/qwen3-30b-a3b-instruct-2507`, `response_format: json_object`
(strict-схемы шлюз не поддерживает — форма задаётся промптом, ответ парсится лениво).

Конвейер `/api/assistant/brief`: текст брифа → LLM → JSON-набор кандидатов →
**`normalize` + `validate` из core** → то, что не чинится правилами, выкидывается с пометкой →
пользователю уходит уже корректный пакет. Квота списывается по факту вызова модели,
остаток показывается в окне ассистента.

🪤 Модель на routerai выгружается при простое: первый запрос после тишины — 30–50 с против 4–6 с
тёплого. На боксе это лечится фоновым keep-alive раз в 3 минуты (сделано в Гермесе) — решим
на ШАГЕ 4, стоит ли греть ради редких запросов.

## 7. Аутентификация

Порт `lib/passphrase.ts` + `lib/auth/session.ts` из pronin: фраза из 5 русских слов + число,
на сервер уходит только HMAC, cookie подписана `AUTH_COOKIE_SECRET`, восстановления нет.

**Секрет `UTMKA_PASSPHRASE_HMAC_SECRET` — свой, не общий с курсом.** Иначе одна и та же фраза
даёт одинаковый hash в двух сервисах, и аккаунт курса связывается с аккаунтом UTMka —
ровно та связность, которой мы избегаем, отказываясь от email. Единый аккаунт между курсом
и инструментом — отдельная фича, не побочный эффект общего секрета.

## 8. Деплой (детали — ШАГ 6)

Бокс `sites-mine` (`5.129.197.27`), стек `/opt/stack`: сервис `utmka`, билд из `./sites/utmka/apps/web`,
`expose: 3000`, сеть `web`, vhost `utmka.alex-pronin.ru` в Caddyfile. Заливка — tar-over-ssh
(у бокса нет доступа к приватным репам, а публичный клон не заводим ради единообразия).

Из граблей бокса, которые нельзя повторить:
- `/opt/stack/Caddyfile` смонтирован как файл → **`sed -i` по нему не работает** (меняет инод, контейнер держит старое). Только дописывание или `cat новый > файл` + `caddy reload`.
- Локальное зеркало `personal/sites-mine-stack/` отстаёт от бокса: перед заливкой compose сверять список `*-edge`-сетей у `caddy` с живым `docker inspect`, иначе чужие домены уйдут в 502.
- После сборки — `docker buildx prune -f`: BuildKit-кэш уже загонял диск на 96%.
- `mem_limit: 400m` + `NODE_OPTIONS=--max-old-space-size=256` (правило STACK.md §3).
- Явное `name:` у compose-проекта, никаких операций над контейнерами соседних проектов.

Env-файл `/opt/stack/env/utmka.env` (chmod 600) — **свой, не `env_file` от pronin**, хотя
`SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` в нём те же значения (общий проект):
`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`,
`UTMKA_PASSPHRASE_HMAC_SECRET`, `AUTH_COOKIE_SECRET`, `ROUTERAI_API_KEY`, `ROUTERAI_MODEL`,
`UTMKA_LLM_DAILY_LIMIT`, `NEXT_PUBLIC_SITE_URL`.

## 9. Дизайн — источники и маршрут

Своей дизайн-системы у UTMka нет и не будет: она **наследуется от «ПРОНИН-ОС»**, иначе получим
третью систему вдобавок к сайту и курсу.

### 9.1 Два эталона (решение владельца 2026-08-10)

**Главная `alex-pronin.ru` — эталон каркаса.** UTMka должна читаться как ещё одно окно той же
операционной системы: рамка устройства, CRT-стекло, таб-бар сверху, статус-бар снизу, маскот
в шапке. Каркас — `components/layout/DeviceShell.tsx` (TabBar → Screen с маскотом → StatusBar),
шапка главной — `components/home/DesktopTopBar.tsx` (аватар + баббл маскота), мобильный вариант —
`MobileTopBar` + `MobileTabBar`.

Перенос на инструмент:
- **таб-бар** — Генератор · Пакет · Разбор · Библиотека · Помощь (место табов главной);
- **статус-бар** — язык, тема, состояние входа (фраза заведена или нет), остаток лимита ассистента;
- **маскот** — в шапке, он же лицо ассистента; на узких экранах уходит в бар, как на сайте.

**Страница `/services` — эталон типографики и плотности.** Она сама помечена в коде как
«образец для будущих страниц»: CRT-медиа без рамок, faux-glass карточки, **радиус 0.125em**,
пиксельные кикеры, акценты magenta/teal, разделитель — блочная шкала загрузки (`LoaderRule`)
вместо линии, маркер секции — пиксельная иконка (`SectionHead`) вместо «§», раскладка `.doc-cols`
со sticky-рейлом на ПК.

**Шрифты берём оттуда же, не подбираем:** `--font-sans` и `--font-mono` — Cascadia Code
(fallback Cascadia Mono → Consolas → IBM Plex Mono), пиксельные акценты — Karmatic Arcade
(`--font-pixel`). Весь интерфейс моноширинный — это и есть узнаваемость «ПРОНИН-ОС».

### 9.3 Объём ШАГА 2

Каркас (рамка, таб-бар, статус-бар, шапка с маскотом) · **генератор в простом режиме, все четыре
шага** · **генератор в расширенном режиме** · тумблер между ними · пакетный режим · библиотека
(шаблоны/справочник/история, три режима отображения) · разбор ссылки · экран кодовой фразы ·

Порядок: сначала каркас и **простой режим** как якорный экран — на нём проверяем, что система
села; остальное наследует утверждённый якорь.
